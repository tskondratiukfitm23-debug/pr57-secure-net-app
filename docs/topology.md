# Топологія стенду

```
  ┌────────────────────────────┐                ┌──────────────────────────────────┐
  │ Вузол «client-node»        │   HTTP  :8080  │ Вузол «secure-server»            │
  │ IP 127.0.0.20 (lo)         │ ─────────────► │ IP 127.0.0.10 (lo)               │
  │ client/client.py, bench.py │   HTTPS :8443  │ uvicorn + FastAPI (server/app.py)│
  │ довіряє лише ca.crt        │ ═════════════► │ server.crt (ECDSA P-256, SAN)    │
  └────────────────────────────┘     TLS 1.3    │ users.json (bcrypt), app.jsonl   │
              │                                 └──────────────────────────────────┘
              │ (демо перехоплення) tools/tap.py: 127.0.0.10:9080→8080, :9443→8443
```

| Вузол | Адреса | Порти | Роль |
|-------|--------|-------|------|
| secure-server | 127.0.0.10 | 8080/tcp (HTTP, лише `/health`, `/echo-http`), 8443/tcp (HTTPS, усі API) | сервер застосунку |
| client-node | 127.0.0.20 | вихідні (ефемерні) | CLI-клієнт, бенчмарк |
| tap (необов'язково) | 127.0.0.10 | 9080, 9443 | пасивний ретранслятор для демонстрації перехоплення |

Клієнт прив'язує вихідні з'єднання до своєї адреси (`--src` / `SNA_SRC`), тому в журналі сервера видно IP клієнта `127.0.0.20`.

**Чому loopback.** Лабораторна ВМ має один мережевий інтерфейс без прав на створення network namespaces чи
додаткових IP. Уся підмережа `127.0.0.0/8` маршрутизується через `lo`, тож різні адреси з неї дають два логічно
окремі вузли з різними IP без додаткових прав.

**Варіант із контейнерами** (`docker-compose.yml`): мережа `lab` 172.28.0.0/24, `secure-server` 172.28.0.10,
`client` 172.28.0.20; сертифікат генерується з SAN `IP:172.28.0.10` і `DNS:secure-server`; сервер працює в режимі
`APP_ENV=prod` (без `JWT_SECRET` не стартує) від непривілейованого користувача.

**E2E у CI**: job `e2e` у GitHub Actions піднімає сервер на окремому раннері й проганяє клієнтські сценарії.
